# Elora implementation decisions

Version 1.0 · 15 November 2026 · Normative companion to [Elora SRS](../specifications/Elora_SRS.md)

The product owner has authorized specification-led development and selection of tools/providers before implementation. These are project decisions, not claims that any service has been configured, purchased, benchmarked or proven best in every comparison. Use this baseline; change it through a reviewed decision with cost, privacy, compatibility and regression evidence. Sources were checked on the date above. Recheck availability, terms, versions and prices at provisioning.

## 1. Selected stack and reasons

| Area | Selected baseline | Reason / implementation boundary |
|---|---|---|
| Mobile | Flutter stable / Dart, Material 3, Riverpod, GoRouter | Preserves repository platform and modular ownership. Lock a mutually compatible stable SDK/package set at bootstrap and commit lockfiles. |
| Mobile integrations | Firebase Auth, FCM; official Flutter camera and image picker; SQLite local store; Android WorkManager integration | Use camera preview for the specified viewfinder and gallery picker for existing photos. Persist the offline outbox; background execution is best effort and foreground resume must work. |
| Localization | Flutter ARB resources, `flutter_localizations` / `intl`; bundled licensed Sinhala/Tamil-compatible fonts | Human-review all three languages; language selection is explicit and retained. Never rely only on runtime machine translation for controls or safety notices. |
| API | Python 3.12, FastAPI, Pydantic 2, SQLAlchemy 2, Alembic, HTTPX | One modular backend, typed contracts, migrations and integration tests. Validate dependency compatibility in the build before pinning exact versions. |
| Database | Managed PostgreSQL 16, `pgvector`, Cloud SQL | Relational ownership, social uniqueness constraints, JSON model metadata and semantic retrieval in one database. No separate vector service or Firestore product store. |
| Crop models | TensorFlow/Keras; EfficientNetB0 transfer-learning baseline, 224×224 RGB; twelve separate categorical models | Starting architecture, not a promised accuracy. Compare with a simple baseline, calibrate, and change architecture only when evaluation justifies it. No on-device inference or TFLite release requirement. |
| Assistant | Google Cloud-hosted Gemini, initial model `gemini-3.8-flash`, via supported Google/LangChain integration | Selected paid provider baseline with image input and typed tool support; not a proven Sinhala/Tamil winner. See release comparison in section 4. Keep model ID configurable and record it on every response. |
| Retrieval | `gemini-embedding-001`, explicit 768-dimensional output, L2 normalization, `pgvector vector(768)` cosine search | Text-only reviewed knowledge; a shared embedding schema replaces older 1,536-dimension assumptions. A model/dimension change requires reindexing and a migration. |
| Agent orchestration | LangChain tools/retrieval, LangGraph with PostgreSQL checkpoints, LangSmith evaluation | Keep the agreed project framework. Backend executes typed actions; the LLM has no database credentials or arbitrary SQL tool. Production LangSmith content tracing disabled by default. |
| Hosting | Google Cloud Run API and private inference service; Cloud SQL; Cloud Storage; Secret Manager; Artifact Registry | Managed deployment and one provider for most infrastructure. Two services isolate inference load without creating twelve model microservices. No Kubernetes, Redis or Celery baseline. |
| Job dispatch/scheduling | Cloud Tasks for immediate authenticated scan-job dispatch; Cloud Scheduler invokes an internal worker every minute; PostgreSQL job state | Tasks invoke inference promptly; Scheduler recovers missed dispatch and handles care reminders, retries, expiry and deletion. Claim rows atomically, use leases and idempotent processing. |
| Notifications | Firebase Cloud Messaging and Android local display | FCM delivery is best effort. In-app care schedules remain the source of truth; duplicate suppression and preferences belong to Elora. |
| Weather/location | Open-Meteo paid customer API; Open-Meteo geocoding / GeoNames attribution | Production licence and quota selected explicitly; do not build a public launch on the free noncommercial endpoint. Local area selection remains available if GPS is denied. |
| Delivery/ops | GitHub Actions, Docker, Terraform, Cloud Logging/Monitoring | PR checks and documented provisioning; workload identity rather than long-lived service account keys. Human-approved production deploy with rollback. |

## 2. Deployment baseline

- Separate development, staging and production configurations, database instances/credentials and buckets. Synthetic test users only in shared developer fixtures. Provider secrets never enter Flutter bundles or Git.
- Start API, inference, Cloud SQL and Cloud Storage in **`asia-south1` (Mumbai)**, subject to actual service availability. Do not claim Sri Lankan data residency. Gemini/embedding endpoints may process outside that region; use the supported Cloud endpoint and document the selected location and transfer terms before release.
- API: initial 2 vCPU / 4 GiB, min 1 instance, max 5, concurrency 20. Private inference: initial 2 vCPU / 8 GiB, min 1, max 3, concurrency 1. These are benchmark inputs, not validated sizing or a provider capacity guarantee. Warm all twelve models and measure RSS/startup time; use bounded loading/caching or resize if required. Fail readiness when the advertised model set is unavailable.
- Cloud SQL: initial PostgreSQL 16, 2 vCPU / 8 GiB zonal instance with SSD and automatic storage growth, private connectivity, encrypted connections, bounded connection pools. Configure at most 5 DB connections per API instance and account separately for workers/migrations. Validate instance availability and pricing; 99.5% is Elora's measured objective, not an inferred Cloud SQL SLA.
- Cloud Run calls the private inference service using a dedicated service identity. Inference accepts only authorized internal object references, never arbitrary user-supplied URLs. API authorizes ownership before signing or fetching an image.
- GCS buckets remain private. Separate operational images, training-consented exports, and versioned model artifacts. Issue short-lived authorized image links (maximum 15 minutes). Do not expose internal bucket paths as public permanent URLs. Re-encode public post photos to strip metadata and validate content before display.
- Scheduler uses OIDC; internal worker routes are not public mobile APIs. Lock each due row, record attempts and acknowledgements, and make processing safe if Scheduler invokes twice. Retry transient failures with bounded backoff; surface failed reminders/cleanup jobs to operations.
- After a scan job is committed, enqueue a Cloud Tasks HTTP invocation with its stable job ID; acknowledge only after the durable result/failure is written. Dispatch failure leaves a pending DB row for Scheduler reconciliation. Authenticate tasks with a dedicated OIDC service identity. Enforce a maximum of 200 global pending/running scan jobs initially; reject excess with 429 before accepting another asset/job. Measure/tune this cap in the load test. Duplicate delivery must claim/return the existing job rather than run a second logical scan.
- Apply an initial 120-second execution deadline after a scan is claimed and a 15-minute maximum pending-job age, then persist a recoverable failure and release the lease. These are safety ceilings, not response-time promises. Retry only transient failures, at most three execution attempts per job, with attempt/lease tokens preventing a late previous worker from overwriting the current result. Benchmark-derived user latency limits must be much more informative than these ceilings.
- Store daily encrypted database backups for 30 days and perform a quarterly restoration drill. Configure object soft-delete retention to 7 days and enforce the SRS deletion deadline across versions/soft-deleted objects. Saved images need protection from accidental deletion; restore tests cover both database references and object availability. Deletion tombstones must be replayed before restored service reopens.
- Logging baseline: 14-day application/operational logs containing request IDs, result codes and timing, without raw messages/photos, passwords/tokens or exact location. Security/deletion audit events: 90 days with pseudonymous event IDs and no retained deleted content. Any legally necessary longer retention must be explicitly justified and disclosed.
- Monitoring: availability probe every minute; alerts for elevated 5xx, model readiness failures, DB pool exhaustion, job backlog/expiry, failed backup and budget thresholds. Assign an operational contact before launch. Alert at 50%, 80% and 100% of the approved monthly budget; alerts are not hard spending caps.

### Cost and procurement gate

No cloud project, subscription or billable resource is created by this specification. Before provisioning production, the integration coordinator produces an estimate using the [Google Cloud calculator](https://cloud.google.com/products/calculator), [Cloud generation pricing](https://cloud.google.com/vertex-ai/generative-ai/pricing), [Firebase pricing](https://firebase.google.com/pricing) and [Open-Meteo pricing](https://open-meteo.com/en/pricing). Include minimum instances, Cloud SQL, storage/egress/backups, Gemini tokens, embedding ingestion, auth/email limits and weather requests. The owner approves the monthly ceiling and account ownership. If the baseline cannot meet that ceiling or the load test, revise sizing openly; do not silently lower scope or availability.

## 3. Authentication and public access

- Firebase manages passwords, email verification, password reset, Google OAuth and account identities. The mobile client obtains a Firebase ID token; the API verifies signature, issuer, audience, expiry and revocation/disabled status with the Admin SDK and maps `uid` to an Elora user. Never accept the email or UID sent as ordinary JSON as authentication.
- Require verified email before scanning, posting or using paid AI; verification/recovery remain accessible. Link providers only from an authenticated session after reauthentication with both appropriate credentials. Do not merge accounts merely because supplied emails match. Provide explicit conflict recovery and unlink protection so an account retains a usable sign-in method.
- Use SDK-managed credential persistence, platform-protected secure storage for any additional secrets, short-lived ID tokens and backend rechecks. This replaces old custom HS256 seven-day JWT/password-hash instructions. Elora does not store passwords.
- Account deletion first marks the Elora account inactive, cancels pending jobs, revokes sessions/refresh tokens and disables its Firebase user. All routes check the inactive flag; deletion of content can then complete asynchronously. Require recent reauthentication to request deletion.
- Public post sharing uses an ordinary HTTPS link to a minimal read-only post page served by the backend; it shows no private plant/scan/chat data. It is not an admin portal or separate web app. Deleted/blocked visibility rules must also apply here; a public recipient without sign-in sees only public post content, never personalized data. Do not use discontinued Firebase Dynamic Links.
- Initial authenticated quotas: at most 20 scan jobs/hour and 100/day/user, 30 assistant turns/hour/user, 10 post creations/hour/user. Use server-enforced distributed DB counters keyed by authenticated UID, with `429` and `Retry-After`; account creation abuse controls and shared IP protection must not lock out an entire mobile carrier. Tune only with recorded load/cost evidence.

### Public community safety — confirmed scope update

On 15 November 2026 the product owner explicitly selected minimal in-app reporting and owner review after reviewing the conflict between public UGC and the earlier blocking-only choice. Include a report reason/target/details form, acknowledgement, restricted report queue, action audit and support/appeal route. The designated owner uses authenticated reviewed operational CLI commands to list reports, remove content and suspend accounts; no admin portal or broad moderator dashboard is added. Ordinary user tokens cannot invoke these commands. Target initial triage within 24 hours, with urgent safety escalation in the runbook. This is a staffed operational obligation, not an automatic promise that every report merits removal. [Google Play UGC policy](https://support.google.com/googleplay/android-developer/answer/9876937?hl=en-GB).

## 4. Assistant and agricultural evidence

- Use paid Google Cloud generation, not an unreviewed free consumer key. Cloud terms restrict training on customer data without permission, but this does not imply zero retention: verify abuse logging, configuration, location, subprocessors and deletion behaviour. [Cloud data governance](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/zero-data-retention), [service terms](https://cloud.google.com/terms/service-terms).
- The chosen Gemini model is a development baseline. Before launch, compare it against at least one supported alternative on the same 90 reviewed cases (30 per language), including retrieval, ambiguous symptoms, unsafe treatment requests, prompt injection, failed tools and write confirmation. Agronomy/language reviewers accept helpfulness, citation correctness and terminology. All prohibited chemical-prescription and unauthorized-write test cases must pass. A failed model must be replaced and retested; merely having API access is insufficient.
- Keep provider/model IDs in configuration; pin deployed configuration and run the evaluation suite before upgrades. Check lifecycle notices monthly. Do not silently use preview models, fall back to a different provider, or send data to a new provider without documented terms and regression review.
- Retrieve only approved, attributed knowledge snippets with source URL/title, publication or access date, crop/region and reviewer status. Use semantic top-5 retrieval, crop/language filters and a minimum-relevance threshold calibrated on reviewed queries. Empty/irrelevant results trigger a limitation statement and follow-up, not invented citations. General cultural advice may be identified as general guidance; treatment options need an approved reference.
- Never embed raw private chats, account identifiers or photos into the public knowledge index. Fetch private context using ownership-checked tools. Send only relevant recent plant/scan/weather fields; include a user-selected attachment only when required for that question. Do not forward account UID/email or the complete garden by default.
- A chat attachment does not automatically run a disease model. If the user asks for a diagnosis, route a supported crop image through the versioned CNN workflow and explain its limits. The LLM must not replace measured CNN confidence with its own invented score.
- Mutation flow: propose a typed action → display exact plant/fields/time → user confirms → backend validates ownership/parameters and executes once → return actual persisted outcome. Confirmation is single-use, expires after 10 minutes and is invalidated if parameters change. Tools may create care logs/reminders and update allowed plant fields; no deletion/account/social publication tool is authorized.
- Limit a turn to 8 tool calls, 2 generation retries and 60 seconds total backend work; return a recoverable timeout and preserve any actual completed action state. Tool writes use a stable idempotency key; never retry an unknown-outcome write as a new operation.
- LangSmith: run evaluation using synthetic or explicitly consented/redacted cases. Production content traces are disabled. Enabling sampled production traces requires privacy review, redaction and a maximum 7-day retention configuration; verify plan support before enabling. Use Cloud logs for normal operational metadata.

## 5. Weather, reminders, XP and offline policies

- Forecast cache: 15 minutes per rounded location/forecast request. When refresh fails, show cached data up to 24 hours old with age and an offline/stale label. Do not generate a new weather-dependent care recommendation from data older than 2 hours. Forecast times use `Asia/Colombo`; persistence remains UTC. Display °C, mm precipitation, km/h wind and humidity %.
- Use seven-day forecasts for planning; recommendations identify the rule/version and inputs. No sensor-derived moisture percentage, exact irrigation volume or yield estimate is claimed. Missing soil/stage inputs produce a bounded explanation and optional questions.
- Notifications are opt-in with per-type settings and default quiet hours 21:00–07:00 Asia/Colombo. Watering/fertilizer reminders are rescheduled to 07:00 if due during quiet hours. Disable server sends when permission/preferences are off; maintain in-app schedules regardless. One scheduled occurrence yields at most one logical reminder, even with multiple registered devices/retries.
- XP baseline: +10 for a distinct accepted watering/fertilizer/pruning care event, maximum 30/day across those categories; +20 for the first weekly photo milestone per plant, maximum 40/week; no XP for scan retries or social activity. Server events determine rewards. Level is `1 + floor(total_xp / 500)`. Badges: first plant, first accepted care event, and care on seven distinct days. Deleting a care entry reverses its associated XP; replay/backdated duplicates do not create new awards. These are product rules, not anti-cheat guarantees.
- Offline: SQLite caches private plants/logs/results and reviewed care text; store at most 200 MB of cached images, evict oldest cached copies only, and retain pending originals until synchronized or explicitly discarded. Allow at most 20 queued scans and 100 pending diary writes; show a full-queue warning before accepting more. A limit never silently discards an entry.
- Process the outbox on foreground resume and opportunistic Android background work. Recheck authentication, account status, plant ownership and asset expiry on every replay. Retry transient failures using exponential backoff up to 30 minutes; validation/conflict failures require user action. Uploads use stable operation IDs. Record both user occurrence time and server receipt time. Append diary entries idempotently; plant edits use revision checks and a conflict resolution prompt. On sign-out clear cached private content after the user resolves/discards pending work; never submit one user's queue under another user.
- Private caches/outbox files stay in app-private storage, excluded from Android cloud backup; use Android device encryption and Keystore-backed keys for any application-managed encrypted values. Never write private photos to a shared gallery automatically. Enforce file/account isolation and clear caches on deletion/sign-out. A user-exported photo is a separate explicit action.

## 6. Build order and minimal developer evidence

1. Shared contracts, auth/profile, migrations, localization/theme/navigation, object upload validation and offline operation IDs.
2. Dataset intake and local collection in parallel with a single genuine end-to-end scan workflow. Temporary mock responses must be labelled and prohibited from production.
3. All twelve model artifacts and reviewed guidance; plant records/history; weather/rules; community/block/share flows; assistant and confirmation tools.
4. Reminders, rewards, offline conflict cases, deletion/restore and security/load/localization/model release evaluation.

Each developer submits links/committed artifacts rather than a documentation essay: dataset manifest, class map, generated metrics/model card, OpenAPI schemas/migrations, and a short PR noting requirement IDs, checks and remaining failures. The rotating integration coordinator owns shared provisioning/runbook/contract reconciliation. The product owner owns scope, spending approval and acceptance; reviewers own agricultural and language approval. Developers may flag infeasible requirements but cannot silently replace the baseline.
